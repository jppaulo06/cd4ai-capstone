\chapter{Case Studies}
\label{chap:case-studies}

This chapter examines how CD4AI's stages appear in Divination and in
the documented workflows of DeepEval with Confident AI, Braintrust, and MLflow.
The evidence varies: Divination provides an inspectable implementation, while
the other cases provide documented workflows and supporting capabilities.
Chapter~\ref{chap:methodology} describes how the cases were selected and
analyzed.

Each case presents its context and evidence, explains how observations move
through monitoring, curation, and evaluation, and examines how results inform
delivery decisions. Case-specific limitations identify what the available
evidence leaves unresolved.

\section{Divination}
\label{sec:case-divination}

\subsection{Context and Evidence}

Divination is a conversational assistant that retrieves passages from a document
corpus to answer questions about Dungeons \& Dragons. This case examines the
evaluation pipeline and testing infrastructure added to Divination.

The inspected revision includes evaluation suites, interaction storage,
candidate signals, and human
review. The evidence consists of versioned source and project documentation,
including the monitoring, evaluation, and CI guides~\parencite{Divination:Monitoring,
Divination:Evaluations,Divination:CI}.

\subsection{The Feedback Loop}

Divination connects stored interactions and human review to a dataset used by
its evaluation suites. A developer manually turns a confirmed defect into a
reusable case~\parencite{Divination:Monitoring,Divination:Evaluations}.
Figure~\ref{fig:case-divination} shows this connection.

\begin{figure}[H]
  \centering

  \caption{Divination's feedback loop. The dashed box marks the manual step
    from a reviewed defect to a dataset case.}
  \label{fig:case-divination}
\end{figure}

\paragraph{Monitoring.}
The application stores questions, answers, and retrieved passages, together
with information about the model, prompt, and document corpus used. Detectors
flag possible problems, such as a numeric claim absent from the retrieved text.
Negative user feedback also generates a signal~\parencite{Divination:Monitoring}.
These signals identify interactions for review; they do not establish defects.

\paragraph{Curation.}
The review panel samples interactions both with and without signals. Reviewers
inspect the answer and retrieved passages, then record a verdict and rationale.
Signals are initially hidden to reduce their influence on the judgment.
Reviewing unflagged interactions also helps reveal failures that the detectors
missed~\parencite{Divination:Monitoring}.
Figure~\ref{fig:divination-review-screen} illustrates this review step.

When the team decides to create an evaluation case for a confirmed defect,
a developer specifies the expected behavior and adds the case to the dataset
stored in the source repository.
Each record contains an opening question, a scenario, and an expected
outcome~\parencite{Divination:Evaluations}. Recording a review does not
automatically add this dataset entry.

\paragraph{Evaluation.}
Divination includes single-turn and conversational evaluations. Both exercise
the application's retrieval and answer-generation flow. The single-turn
evaluation submits the case's opening question and assesses the answer using
the selected criteria. In Divination, these include checking whether the
answer's claims are supported by the retrieved passages and agree with the
expected outcome.

The conversational evaluation simulates a user interacting with the application
over several turns. The simulated user generates follow-up messages based on
the scenario and the conversation so far. The resulting conversation is then
assessed using criteria such as whether the assistant's claims are supported
by the retrieved passages~\parencite{Divination:Evaluations}.

\subsection{Result Interpretation and Delivery Decisions}

The case-creation guide instructs the developer to check that a new case
exposes the defect, run it again with the proposed fix, and commit the case
with the fix~\parencite{Divination:Evaluations}. The intended sequence is
confirmation followed by regression protection: check that the change addresses
the problem, then retain the case for later changes. One passing run may not
establish that an intermittent defect has been fixed, as discussed in
Section~\ref{sec:cd4ai-result-interpretation}.

The CI pipeline runs the single-turn evaluations automatically on pull requests
using DeepEval, the evaluation framework examined alongside Confident AI in
Section~\ref{sec:case-deepeval}. If an evaluation fails its required checks,
the CI job is marked as failed~\parencite{Divination:CI}.

\subsection{Limitations and Possible Improvements}

The pipeline connects reviewed defects to evaluations that run in CI. Further
improvements could make it clearer which problems those evaluations cover and
what their results mean for delivery.

The current procedure adds an evaluation case together with the fix for
the defect it captures. It could be extended to include cases whose defects
have not yet been fixed. Recording which problems are already known and
comparing results with a reference application version would help distinguish
continuing failures from new or worsened behavior. The team could then define
which known failures can be tolerated for delivery and which results should
block a proposed change.

Interpreting these results also requires knowing whether the assessments
completed. The evaluation setup allows the run to continue when an assessment
encounters
an execution error or lacks required information. For example, an LLM judge
may return an answer that the evaluator cannot parse. A successful CI job
therefore does not guarantee that every assessment was completed. The CI
summary could make this explicit by separating completed assessments that
passed or failed from those that were skipped or encountered errors. These
options do not implement a policy for tolerating known defects: they handle
assessments that could not be completed, rather than answers assessed as
incorrect.

The coverage of these evaluations also depends on turning selected reviewed
defects into cases that the pipeline can evaluate. This step currently
requires manual work.
Linking the review record to the resulting case would make it easier
to see which reviewed defects have corresponding evaluation cases.

\section{DeepEval and Confident AI}
\label{sec:case-deepeval}

\subsection{Context and Evidence}

DeepEval is an open-source framework for evaluating LLM applications. Confident
AI, the company that maintains it, also offers a platform for monitoring,
evaluation reports, and collaborative dataset
management~\parencite{ConfidentAI:DocsIndex}. In the workflow examined here,
DeepEval runs evaluations, while Confident AI supports monitoring, review,
and comparison of evaluation results. The evidence consists of their guides on
evaluation, monitoring, annotation queues, dataset management, and
Experiments~\parencite{ConfidentAI:Experiments}.

\subsection{The Feedback Loop}

DeepEval's conversational guide connects production monitoring to development:
failing conversations can become evaluation cases added to the development
dataset~\parencite{DeepEval:MultiTurn}. Figure~\ref{fig:case-deepeval} shows
the capabilities supporting this return path.

\begin{figure}[H]
  \centering
  \input{figures/case-deepeval}
  \caption{The feedback loop across DeepEval and Confident AI. Workflow rules
    can route interactions to review queues or directly to datasets for review.}
  \label{fig:case-deepeval}
\end{figure}

\paragraph{Monitoring.}
Confident AI helps the team find interactions worth reviewing. It records
application executions and conversations so that they can be inspected and
assessed. Automated checks, called metrics, score aspects of application
behavior, while classifiers assign labels to
interactions~\parencite{DeepEval:MultiTurn,ConfidentAI:OnlineEvals,
ConfidentAI:Classifiers}.

For example, classifiers can label interactions as expressing negative
sentiment. Signals highlights increases in such labels, and Failure Modes
groups flagged interactions into recurring problems and provides examples
for review~\parencite{ConfidentAI:Classifiers,ConfidentAI:Signals,
ConfidentAI:FailureModes}. User ratings and comments provide another source of
candidates~\parencite{ConfidentAI:AnnotationQueues}.

The Drift view compares production results across application versions and
flags sustained deterioration relative to a selected reference
version~\parencite{ConfidentAI:Drift}. These findings help the team identify
changes worth investigating after deployment.

\paragraph{Curation.}
Annotation queues organize selected interactions for human review. Reviewers
can record a rating, an explanation, and an expected answer or conversational
outcome~\parencite{ConfidentAI:AnnotationQueues}. Confident AI's Workflows
automate the selection and routing of interactions. The team defines conditions
that trigger an action, such as sending an interaction to a review queue or
adding it to a dataset for review in the dataset
editor~\parencite{ConfidentAI:Workflows,ConfidentAI:Datasets}.

DeepEval calls the retained records \emph{goldens}. A single-turn golden stores
an input and may include a reference answer or context. A conversational golden
describes a scenario and its expected outcome, without prescribing every
message~\parencite{ConfidentAI:Datasets,DeepEval:MultiTurn}. For example, a
golden could describe a customer requesting a refund after 45 days, with the
expected outcome that the assistant explains the 30-day refund limit.

Together, these records form the evaluation dataset. Team members review the
prepared cases in the dataset editor and mark them as ready for evaluation,
a step called \emph{finalization}~\parencite{ConfidentAI:Datasets}. A finalized
case may still expose an unresolved defect in the application.

\paragraph{Evaluation.}
DeepEval evaluates an application version using cases retained in a dataset.
For single-turn evaluations, the application answers each stored input. For
conversational evaluations, a simulated user interacts with the application
according to a retained scenario. Metrics define how the resulting answers
or conversations are assessed. Depending on the metric, this assessment may
use code or an LLM acting as a judge. Some metrics use the case's expected
answer or outcome as a reference~\parencite{DeepEval:AgentGuide,DeepEval:MultiTurn}.

The team selects metrics for the cases being evaluated. A common setup applies
the same set of metrics to every case in a run, with each assessment using the
information provided by that case. Cases requiring different checks can
instead be evaluated with different metric
selections~\parencite{DeepEval:AgentGuide,DeepEval:CI}.

For example, the team could apply the same correctness metric to two refund
cases. This metric uses an LLM judge to compare each actual answer with its
corresponding expected answer, without requiring identical wording. For a
purchase made 45 days ago, the expectation is to explain that the 30-day refund
window has expired; for a purchase made 10 days ago, it is to explain that the
purchase qualifies. The assessment logic remains the same, while the expected
answer varies by case.

Different metrics assess different aspects of behavior.
A metric configured to assess politeness, for example, could give a high score
to a courteous answer that makes the wrong refund decision. Recording the
expected answer therefore does not ensure that every selected metric checks
it. The team needs to choose assessments that cover the behavior the case is
intended to verify. The resulting outputs and assessment results are collected
in a \emph{test run}~\parencite{DeepEval:AgentGuide,DeepEval:MultiTurn}.

The following subsection explains how these results support comparisons
between versions and acceptance checks in CI.

\subsection{Result Interpretation and Delivery Decisions}

Confident AI's \emph{Experiments} compare application versions using the same
dataset and metrics. In the documented workflow for existing single-turn
results, a user selects test runs in the interface and creates an Experiment.
The platform displays the selected test runs side by side, including average
scores, differences relative to a selected base run, and the outputs and scores
for individual cases~\parencite{ConfidentAI:Experiments}. The selected runs
may include results previously produced in CI.

In CD4AI, this comparison can help distinguish continuing limitations from
potential regressions. For example, a retained case might score poorly in both
versions, while another case's score drops after a change. The first result
suggests a continuing limitation; the second suggests deterioration to
investigate.

Comparing versions helps the team investigate changes, but delivery also
requires deciding whether the results are acceptable. DeepEval can run
selected evaluations automatically in CI. Teams can use metric thresholds to
define acceptance checks or implement their own rules---for example,
comparing results with a chosen reference run and rejecting score decreases
beyond an accepted tolerance.

With threshold-based checks, each required metric must meet its acceptance
threshold for the evaluated case. If a required check fails, the test fails
and CI marks the job as failed. Passing results on other cases do not cancel that
failure~\parencite{DeepEval:CI}.

DeepEval also allows cases or metrics to be marked as \emph{flaky}, so their
failures remain visible without failing the CI
test~\parencite{DeepEval:CI}. This mechanism is documented for intermittent
failures; its possible use for known unresolved defects is discussed below.

Confident AI supports designating an \emph{official reference run}, a saved evaluation
run used as a reference for subsequent comparisons~\parencite{DeepEval:CI}.
This designation alone does not make CI reject deterioration relative to that
run; enforcing such a comparison requires a rule implemented by the team.

\subsection{Limitations}

DeepEval and Confident AI provide mechanisms for retaining evaluation cases,
comparing application versions, and enforcing acceptance checks in CI. Putting
these mechanisms together, however, leaves an important decision to the team:
how to allow known unresolved problems while detecting unacceptable
deterioration.

Threshold-based checks assess results against acceptance criteria. On their
own, they do not identify deterioration relative to an earlier version.
Suppose a metric requires a score of at least 0.70. A
decrease from 0.95 to 0.75 would still pass, even though the measured behavior
has worsened. Conversely, a case scoring 0.60 in both versions would fail
without indicating a new regression. A failed CI check therefore does not, by
itself, distinguish a continuing limitation from a regression.

Experiments help address this distinction by displaying differences between
application versions. In the documented workflow, however, a user initiates
the comparison through the interface and interprets its
results~\parencite{ConfidentAI:Experiments}. Relying on this review for each
proposed change may become burdensome as the number of changes and evaluation
cases grows.

Even when a problem is identified, the team may need to deliver a version
before resolving it. The \texttt{flaky} flag offers a possible way to keep an
unresolved case under evaluation without blocking CI~\parencite{DeepEval:CI}.
However, allowing its failures also means that the check alone will not block
further deterioration. For example, a case that previously failed occasionally
could begin failing consistently while remaining non-blocking. Using this
mechanism for known issues therefore requires a separate policy for reviewing
their results and deciding when they are no longer acceptable.

Deciding whether such behavior has worsened becomes harder when failures are
intermittent. Even under unchanged
conditions, repeated evaluations may produce different outcomes. A failure in
the proposed version may therefore reflect variation rather than a regression.
Repeated evaluations can help establish whether the behavior has become less
reliable---for example, whether a case that previously failed in roughly one
out of ten executions now fails in six out of ten. The team must still decide
how much evidence is needed to treat that difference as meaningful. Marking
the case as flaky prevents it from blocking CI, but does not resolve this
uncertainty.

\section{Braintrust}
\label{sec:case-braintrust}

\subsection{Context and Evidence}

Braintrust is a commercial platform for observing, reviewing, and evaluating AI
applications. Its documentation describes five stages (instrument, observe,
annotate, evaluate, and deploy) that form a feedback
loop~\parencite{Braintrust:Workflow}. The evidence consists of the documentation
for that workflow and for monitoring, human review, datasets, experiment
comparison, and CI.

Two terms describe how Braintrust organizes evaluations. A \emph{scorer}
assesses an application output and returns a score between 0 and
1~\parencite{Braintrust:Scorers}. It plays a role similar to a DeepEval metric
(Section~\ref{sec:case-deepeval}): the same scoring logic can assess different
cases, using each case's expected output as a reference when needed. An
\emph{experiment} records the outputs and scores of one evaluation run, similar
to a DeepEval test run, and can be compared with other
experiments~\parencite{Braintrust:DatasetUse,Braintrust:Comparison}.

\subsection{The Feedback Loop}

Figure~\ref{fig:case-braintrust} maps Braintrust's documented features to
CD4AI's three stages.

\begin{figure}[H]
  \centering
  \input{figures/case-braintrust}
  \caption{Braintrust's feedback loop. The dashed box marks the custom rule
    the team defines to turn evaluation results into a CI decision.}
  \label{fig:case-braintrust}
\end{figure}

\paragraph{Monitoring.}
Logs retain application interactions as traces that can later be reviewed.
Recording those interactions makes review possible, but the team still needs
to identify which ones deserve attention. Dashboards help by showing trends
in scores, latency, and costs~\parencite{Braintrust:Dashboards}. A concerning
trend can prompt reviewers to investigate individual interactions and assess
what went wrong.

Patterns provides another way to identify candidates for review. Braintrust's
AI agent investigates traces and reports recurring problems, with supporting
traces for each finding~\parencite{Braintrust:Patterns}. This can draw
attention to problems that the configured scorers do not capture: the scores
reflect the criteria being assessed, which may not cover every kind of
undesired behavior. Reviewers can inspect the supporting interactions to
determine whether a reported pattern represents a problem that warrants
further action.

Candidates can also come directly from end users. The application can attach
their feedback to the corresponding trace as ratings, comments, or
corrections. A correction states what the user thinks the output should have
been~\parencite{Braintrust:UserFeedback}. This feedback can point to
interactions worth reviewing even when automated checks have not flagged them,
but it does not by itself establish a defect. A negative rating indicates
dissatisfaction, and a correction may itself be mistaken. For example, a
customer could reply that the assistant should have approved a refund, even
though the purchase falls outside the refund window. Assessing the
interaction and the user's feedback belongs to the subsequent curation stage.

\paragraph{Curation.}
Reviewers assess selected traces and record what the application should have
produced in the trace's expected field. They can choose from predefined
options, such as the correct label for a classification task, or write the
expected output as free text~\parencite{Braintrust:HumanReview}. The recorded
expectation can then serve as the reference a scorer uses to assess later
outputs~\parencite{Braintrust:DatasetUse}. Corrections from end users are also
recorded as expected values~\parencite{Braintrust:UserFeedback}. Because a
correction may be mistaken, CD4AI treats it as a candidate: a reviewer checks
it before it serves as a reference.

Selected traces can then be added to a dataset from the logs or review
views~\parencite{Braintrust:Datasets}. In Braintrust, a dataset is a versioned
collection of evaluation cases. Each record contains an input and may include
an expected output, metadata, and
tags~\parencite{Braintrust:DatasetOverview}. For the refund example, a record
could contain the customer's question and the expected response under the
refund policy. The dataset stores the cases; running the application and
assessing its outputs produces the experiment results.

\paragraph{Evaluation.}
The team specifies the dataset, the application function to execute, and the
scorers that assess its outputs. A dataset can be selected by name and version
so that later edits do not change the cases used in the
evaluation~\parencite{Braintrust:DatasetUse}. Experiments can run each input
several times as \emph{trials}, exposing behavior that varies between
executions~\parencite{Braintrust:Comparison}.

\subsection{Result Interpretation and Delivery Decisions}

Selecting a dataset determines which cases an evaluation runs. Selecting a
\emph{baseline} determines which saved experiment supplies the reference
results. In Braintrust's comparison view, the team can select another experiment
as the baseline. For example, it could compare a proposed change with an
experiment run on the deployed application. By default, Braintrust matches
cases by their inputs and displays their scores and score differences side
by side~\parencite{Braintrust:Comparison}.

Score decreases appear in red and improvements in green. Reviewers can filter
or sort the cases Braintrust labels as regressions~\parencite{Braintrust:Comparison}.
In the terms of Section~\ref{sec:cd4ai-result-interpretation}, these are
potential regressions. A case that scores poorly in both experiments may
indicate a continuing limitation; a further decrease may indicate that the
limitation has worsened.
Figure~\ref{fig:braintrust-comparison-screen} shows a comparison with repeated
executions grouped under the same input.

\begin{figure}[!htbp]
  \centering
  % The source is 144 dpi. Show the first input group and its score column.
  \includegraphics[trim={92.5bp 191bp 441bp 90bp},clip,width=\linewidth]
    {braintrust-comparison-source.png}
  \caption[Braintrust's comparison view grouped by input]{Braintrust's
    comparison view, grouped by input. The expanded case contains three trials,

The experiments may contain only some of the same cases. Suppose the baseline
contains A and B, while a later experiment also includes a newly curated case C.
A and B can be compared, but C has no baseline result. Braintrust shows a
missing comparison value when inputs cannot be matched~\parencite{Braintrust:Comparison}.
C can still be assessed against its criteria. To compare its behavior across
versions, the team could run the reference application version on the expanded
dataset as well.

The same example explains why comparing overall averages needs care. A
difficult case C could lower the average without any deterioration on A or B.
The guide recommends selecting a baseline from the same dataset when choosing
one automatically~\parencite{Braintrust:Comparison}. Because datasets can
evolve, the name alone does not ensure that the cases are identical: comparisons
need a common set of cases and compatible assessment criteria.

Showing a score decrease in the comparison view does not automatically make
it block delivery. In CI, an action runs evaluations on pull requests and
posts a comparison summary~\parencite{Braintrust:Comparison}. By default, an
exception raised during evaluation makes the evaluation command fail. This
indicates an execution error; an evaluation that completes but produces lower
scores does not fail the command for that reason alone~\parencite{Braintrust:CI}.

This also differs from DeepEval, where a metric's threshold determines whether
a test passes and a failed test fails the CI job. A Braintrust scorer can be
given an optional pass threshold, which marks its scores as passing or failing
in the experiment view~\parencite{Braintrust:Autoevals}. The reviewed
documentation does not describe this threshold as affecting the CI outcome.

To make these scores affect the CI outcome, the team defines a \emph{custom
reporter}: code that processes evaluation results and decides whether they
should make the CI job fail~\parencite{Braintrust:CI}.

The comparison summary is also available to code~\parencite{Braintrust:Comparison}.
A reporter could therefore implement a rule that tolerates continuing failures
but blocks potential regressions, including worsening behavior on cases that
already failed. This is a possible implementation; the reviewed sources do not
specify such a policy for handling known limitations.

\subsection{Limitations}

Braintrust makes differences between experiments visible and allows teams to
use them in CI decisions. Using these comparisons for regression protection
still requires choosing an appropriate reference, interpreting the observed
differences, and deciding which differences should block delivery.

The reference needs to represent behavior that the team intends to preserve.
With Git metadata and no
explicit baseline, Braintrust selects the most recent experiment on the same
branch~\parencite{Braintrust:Comparison}. That experiment may itself have been
a failed attempt, rather than a version whose behavior the team accepted.
The team therefore needs to check whether the selected baseline is appropriate
for the delivery decision.

Even with an appropriate reference, a score decrease may reflect variation
between executions. The comparison guide does not describe a statistical test
that distinguishes score decreases from run-to-run variation, although trials
make that variation visible~\parencite{Braintrust:Comparison}. A reported
decrease therefore needs investigation before it is attributed to an
application change.

Once the team has interpreted a difference, it must decide how that result
affects delivery. The custom reporter provides a place to enforce this policy,
but does not define it. For example, the team may tolerate a continuing known
failure while rejecting further deterioration on the same case. The reviewed
workflow leaves this distinction to the team, so displaying a comparison alone
does not establish how known limitations and potential regressions will be
handled in CI.

\section{MLflow}
\label{sec:case-mlflow}

\subsection{Context and Evidence}

MLflow is an open-source platform with capabilities for tracing, human review,
evaluation datasets, and scoring. The evidence consists of its guides on
regression testing, review queues, and datasets~\parencite{MLflow:RegressionGuide,
MLflow:ReviewQueues,MLflow:Datasets}, together with a Databricks guide on its
managed MLflow offering~\parencite{Databricks:QualityLoop}.

\subsection{The Feedback Loop}

Databricks describes a quality loop: review traces, curate a dataset, define
a scorer, modify the application, evaluate the fix, and monitor production
again~\parencite{Databricks:QualityLoop}. MLflow's testing guide complements
this sequence with tests that capture observed failures and run on subsequent
changes~\parencite{MLflow:RegressionGuide}. Figure~\ref{fig:case-mlflow} maps
these activities to CD4AI. Preparing the case and its criteria belongs to
curation; implementing the application fix is part of development.

\begin{figure}[H]
  \centering
  \input{figures/case-mlflow}
  \caption{MLflow's feedback loop. The related Databricks quality loop also
    describes applying scorers to live traffic during monitoring.}
  \label{fig:case-mlflow}
\end{figure}

\paragraph{Monitoring.}
Traces record inputs, outputs, and intermediate model calls, tool use, and
retrieval steps, allowing the team to inspect where an interaction went
wrong~\parencite{Databricks:QualityLoop}. Negative user feedback can identify
candidates for review~\parencite{MLflow:RegressionGuide}. The Databricks
quality loop also uses scorers on live traffic to find recurring or new
problems~\parencite{Databricks:QualityLoop}.

\paragraph{Curation.}
Review queues organize selected traces and the questions reviewers should
answer. Questions can ask for feedback on the observed output or for an
expectation describing what the application should have produced. Answers
are stored on the reviewed trace~\parencite{MLflow:ReviewQueues}.

The team can export selected traces to a new or existing evaluation dataset,
a collection of inputs that may include expected outputs. Expectations can
be added before or after export~\parencite{MLflow:Datasets}. Alternatively,
the team can write a test containing the input and checks for the desired
behavior~\parencite{MLflow:RegressionGuide}. Both approaches make the reviewed
situation available for later evaluation.

\paragraph{Evaluation.}
The team supplies the application function, evaluation data, and scorers.
MLflow runs the function on the inputs and assesses its
outputs~\parencite{MLflow:RegressionGuide}. The retained cases support
assessing fixes, comparing versions, and checking established
behavior~\parencite{MLflow:Datasets}. A scorer used here may also assess live
interactions during monitoring, as described in the Databricks quality
loop~\parencite{Databricks:QualityLoop}.

\subsection{Result Interpretation and Delivery Decisions}

The regression-testing guide distinguishes measuring performance from enforcing
acceptance criteria. A dataset evaluation can report scores across cases, such
as the proportion of answers judged correct. A test uses assertions to require
specified criteria to pass~\parencite{MLflow:RegressionGuide}. The two uses
can share data and scorers; what differs is how the results affect a decision.

In the guide's example, every scorer must pass for every included case. A
failed assertion fails the test and CI job, and MLflow records the checks and
their explanations for inspection~\parencite{MLflow:RegressionGuide}. For
example, a check could require an answer to follow a refund policy; its failure
would fail the test even if other answers scored well.

The dataset guide also describes comparing application versions on the same
data~\parencite{MLflow:Datasets}. This can help assess whether a fix improves
a retained case, whereas the assertion checks whether the current result meets
its criteria.

\subsection{Limitations}

MLflow's guides connect observed failures to tests that can enforce acceptance
criteria. The remaining question is how to interpret a failed check: does it
expose a problem that remains unresolved, or behavior that has deteriorated?

The illustrated assertion does not distinguish a continuing failure from one
introduced by a change. An included case that fails its criteria fails the
check in either situation. The reviewed sources do not specify how known
limitations would remain visible while some failures are permitted and others
block delivery.

Making this distinction requires evidence of earlier behavior. The guides
describe creating tests from observed failures and assessing fixes. A case
created while a defect remains unresolved may continue to fail until the fix
is effective. Calling such checks regression tests expresses their intended
protective use; it does not establish that the application previously passed
them. Interpreting a later failure as a regression therefore requires a
reference showing the behavior that had been established, as discussed in
Section~\ref{sec:cd4ai-result-interpretation}.
